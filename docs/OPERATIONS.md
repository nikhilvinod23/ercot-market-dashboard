# Publication and scaling

The public dashboard is a static GitHub Pages application. Opening or reloading it does not launch the server collector. Its browser checks a small status.json every minute while visible and downloads new datasets only after their publication timestamp changes. Source timestamps and publication timestamps are distinct; a successful publication can still contain a retained stale source.

GitHub Actions targets collection at minutes 23 and 53, publishes on changes to the deployment branch, and supports manual dispatch and repository_dispatch with event_type collector_tick. GitHub cron is best effort: inspected runs on October 10–13 had several-hour gaps despite an hourly schedule. More frequent scheduling reduces expected gaps but cannot guarantee 30-minute freshness. For a strict service target, use an independent hosted scheduler to send collector_tick after a public status check finds publication older than 75 minutes, or run the collector on a continuously available host. Do not place a GitHub access token in the browser. Authenticate scheduler calls server-side with narrowly scoped repository access. Use the existing workflow concurrency group to avoid overlapping archive writers.

Data health links to the collector workflow so an authorized user can use Run workflow to recover a stale edition. Failed runs retain the SQLite archive and generated data as a seven-day recovery artifact. Monitor publication age, source age, failed sources, run duration, ingestion lag, archive size and missing operating-day intervals. Alert after 75 minutes of publication age and after two consecutive source failures; distinguish slow source publication from scheduler failures.

## Current optimizations

- SQLite indexes cover target time and collection time. The daily text-ledger exporter skips unchanged partitions using append-only row counts and limits shards to 25,000 records. The portable ledger still restores the entire database in a new Actions runner.
- Browser polling uses conditional HTTP caching and a publication manifest rather than downloading several megabytes every minute. Hidden tabs pause polling and resume on visibility. Only the displayed view renders, and chart tables populate when expanded.
- Recent chart payloads and report retention remain bounded. Full observation and forecast-vintage archives remain outside browser payloads. Charts fit their container and expose exact values through touch, keyboard and data tables.

## Next architecture when the archive grows

Make a persistent PostgreSQL database the ingestion source of truth; the existing DATABASE_URL integration is a mirror and does not yet replace the ledger. Enforce immutable observations, unique ingestion IDs, source-issued and first-seen timestamps, and one writer per feed. Partition larger tables by delivery month and index location/metric/time. Archive immutable daily or monthly Parquet files in object storage, with checksums and a retention policy that preserves all forecast vintages needed for research. Keep source code and operational configuration in Git; avoid using Git history as the long-term high-frequency data store.

Separate ingestion from aggregation and publication: retry individual failed sources, retain valid prior readings with their original timestamps, build a consistent completed snapshot, then atomically update its manifest. Generate hourly/day/month aggregates and publish small data files per view and operating day. Load map frames and older reports on demand. Keep min/max envelopes when downsampling charts so scarcity spikes are not smoothed away. Use compressed HTTP responses, ETags and immutable versioned files at the CDN. Serve queried history through pagination or date-bounded endpoints rather than sending the entire archive to mobile devices.

## Kalshi research

The collector reads public KXTXERCOTPEAKD market metadata and current quotes without an account key. It stores bid/ask sizes, spreads, volume and open interest in the same observation ledger, and retains contract dates, rules and settled outcomes. It extracts the operating day from contract rules, because the ticker often uses the following date. Source settlement is currently Kalshi's reported expiration value, representing the specified first complete ERCOT hourly-load report; it is not the dashboard's instantaneous peak.

The UI compares source-issued pre-midnight ERCOT forecast peaks to settled peaks and indicates whether the forecast was actually captured before delivery. Quote history starts with this collector; it is not invented by interpolating terminal prices. Brier scores use the first two-sided quote observed in each 09, 12, 15 and 18 Central hour, before market close. Missing hours are omitted. Contract samples within one day are correlated; count resolved days separately. No optimal trade hour is claimed without historical strategy tests on unseen operating days.

For credible trading research, archive frequent order-book snapshots or streamed deltas on a persistent host, alongside complete public trade history and rule/fee changes. Use separate quote, trade and receipt times. Backfill historical candlesticks through Kalshi's live/historical endpoints, but do not mistake OHLC price history for historical executable size or assume a resting order would fill. Define a forecast probability model and trade policy before evaluation; compare fixed entry windows, simulate entry asks/exit bids with depth and fees, measure fills, drawdowns and after-cost returns, and validate on future days. The current calculator is a scenario tool, not order execution or an established trading strategy.
